# 三核心交叉技能｜八字命盤 × 紫微斗數 × 易經卜卦

> **口令：「三合一」**
>
> 使用者只要說「三合一」，就代表這三樣：**八字命盤、紫微斗數、易經卜卦**。
> 收到口令即執行下方〈六、三合一執行程序〉。

> 定案 2026-09-04。這是命理運算的架構鐵律，任何新卡片、任何引擎改動都適用。

---

## 一、三層順序（不可顛倒）

```
第一層  八字命盤   核心。唯一的四柱來源。
   ↓
第二層  紫微斗數   第二輪。消費第一層，不得自行推算四柱。
   ↓
第三層  易經卜卦   第三輪。只負責「怎麼說」。
   ↓
        前端      只顯示。不編結論、不自己算、不自己寫解讀。
```

**一切以八字命盤為主。** 前一層算完並凍結之後，後一層才開始；後一層永遠不能回頭改寫前一層的結論。

---

## 二、每一層的職責與禁令

### 第一層｜八字命盤（核心）

| | |
|---|---|
| 唯一入口 | `lib/bazi/engine.ts` 的 `createBaziCore()` |
| 產出 | 年、月、日、時四柱、日主、十神、藏干、大運 |
| **禁令** | **任何模組不得自己再實作一套四柱推算** |

年界以立春、月界以節氣、晚子時不換日——這些規則只存在於這一支引擎裡。

**判準素材**（專業命理師客訴後永久鎖定，`tests/bazi-core.test.ts`）：

```
1974-07-02 03:30 女 → 甲寅／庚午／甲辰／丙寅
  月柱＝庚午：小暑(7/7)前仍屬午月，甲年五虎遁，不是辛未
對照組 1974-07-08 → 辛未（小暑後）
```

### 第二層｜紫微斗數

| | |
|---|---|
| 排盤入口 | `lib/ziwei/chartEngine.ts` 的 `generateZiweiChart()` |
| 三方四正 | `lib/ziwei-sanfang-engine.ts` |
| 八字欄位 | **必須取自第一層**，不得自算 |
| **禁令** | 時辰未確認時不得硬排命宮，也不得代填午時 |

排盤本身（命宮、十二宮、十四主星、四化）獨立於八字，但凡是回應裡出現的四柱，一律來自第一層。

### 第三層｜易經卜卦

| | |
|---|---|
| 起卦 | `lib/iching-engine.ts` 的 `castHexagramFromBirth()`（梅花易數，決定性） |
| 格局名 | `lib/iching-psychology.ts` 的 `patternNameOf()` |
| 話術 | `buildEmpathicFromHexagram()` 等共感層 |
| **禁令** | **不新增規則、不改寫證據**。哪個月、哪個方向，全部來自前兩層 |

現成正確範例：`lib/red-luan-iching-reading.ts` 開頭的分層宣告。

**話術由這一層產出，交給前端顯示。** 這是「前端不准編結論」的正面說法——不是叫前端別寫，是告訴它「文案在易經層，去拿」。

### 前端

只顯示。三條紅線：

1. 不得自己計算任何看起來像運算結果的數字
2. 不得自己寫解讀文字（要就放進易經層）
3. 不得端出系統自己否認的宣稱

## 三、鐵律＝必生 CI 測試

> **以後只要立下這種鐵律，就要同時生出一支 CI 測試。**

沒有測試的鐵律等於沒有鐵律。紫微卡的日柱錯了不知道多久，就是因為當時只有口頭原則、沒有機器在守。

現行守門測試：`npm run test:three-core`（41 項斷言）

| 層級 | 斷言 |
|---|---|
| 八字 × 紫微 | 6 組生辰的四柱必須完全一致 |
| 獨立錨點 | 日柱必須對得上 1974-07-02＝甲辰 的純日數推算（不經任何命理引擎） |
| 卡內一致 | `meta.dayPillar` 與 `ziweiSanFang.bazi.day` 不得矛盾 |
| 正統鎖定 | 1974-07-02 逐柱釘死＝甲寅／庚午／甲辰／丙寅 |
| 易經決定性 | 同一生辰起卦 50 次必須完全相同 |
| 易經可回查 | `seedText` 必須帶生辰與時辰 |
| 易經有效性 | 時辰不同必須是不同的卦；不同生辰不得塌成同一卦 |

邊界覆蓋：節氣換月前後一天、晚子時、閏年 2/29、跨年 12/31。

**新增鐵律時的最低要求**：一個正向案例、一個邊界案例、一個**反向驗證**（故意注入該類錯誤，確認測試會爆）。

---

## 四、這條鐵律怎麼來的

2026-09-04 巡檢《易經紫微斗數》時發現：

`lib/ziwei-sanfang-engine.ts` 用 `tyme4ts` 的 `LunarHour.fromYmdHms()` 自行重算了一份八字，
而該 API 吃的是**農曆**、程式卻餵**國曆**。1990-05-20 被當成農曆五月二十（實際國曆 6/12），
整整差 23 天：日柱算成戊申（正確乙酉）、日主變成戊土（正確乙木），整段流年生剋關係相反。

最致命的是——同一份回應裡 `meta.dayPillar` 是對的、`ziweiSanFang.bazi.day` 是錯的。
兩套八字各自內部一致，所以**各自的測試都過**，因為從來沒有人把它們放在一起比對。
客戶只要拿八字卡與紫微卡對照一次就會發現。

問題不是演算法錯，是**同一件事被算了兩次，而沒有人負責比對**。
所以鐵律不是「要算對」，是「**只准算一次，而且要有機器守著**」。

## 五、新增卡片時的檢查清單

- [ ] 需要四柱嗎？→ 呼叫 `createBaziCore()`，不要自己寫
- [ ] 需要命盤嗎？→ 呼叫 `generateZiweiChart()`，八字欄位取自第一層
- [ ] 需要話術嗎？→ 寫在易經層，前端只顯示
- [ ] 前端有沒有自己算的數字或自己寫的解讀？→ 搬回引擎
- [ ] 有沒有端出後端否認過的宣稱？→ 拿掉
- [ ] 這張卡的四柱有沒有進 `test:three-core`？→ 加進去
- [ ] 新鐵律有沒有對應的 CI 測試？→ 沒有就不算立法完成

## 六、三合一執行程序

收到口令「三合一」時，依序執行並回報：

### 步驟 1｜跑守門測試
`npm run test:three-core` — 41 項斷言必須全綠。有紅就先停，報告哪一項。

### 步驟 2｜同一組生辰實跑三層
用同一筆出生資料，依序取得三層輸出並逐項核對：

| 檢查 | 判準 |
|---|---|
| 第一層 八字四柱 | 對得上獨立錨點（1974-07-02＝甲辰，純日數推算） |
| 第二層 紫微四柱 | 必須與第一層**完全一致** |
| 卡內一致 | `meta.dayPillar` 不得與 `ziweiSanFang.bazi.day` 矛盾 |
| 第三層 易經卦象 | 決定性、可回查、時辰不同必不同卦 |
| 前端 | 沒有自編結論、沒有自算數字、沒有已被否認的宣稱 |

### 步驟 3｜三大核心對照（米其林）
- **品質**：前端不准編結論
- **服務**：免費也要尊榮
- **穩定**：沒驗過不准上線

### 步驟 4｜回報
逐層列出實測值（不是「應該正常」），有問題就給 P0/P1/P2/P3 分級與解法。
**不得只報結論不附數據。**

## 七、逐卡三合一（方法要能對準單一張卡）

「三合一」不只是跑一次全域檢查——它是**方法**，要能對準任何一張卡，
驗那張卡自己的八字、紫微、易經是否與三個核心一致。

### 逐卡檢查表

| 層級 | 對這張卡問什麼 |
|---|---|
| 第一層 八字 | 這張卡的四柱／年支／日支，是不是來自 `createBaziCore()`？有沒有自己算一套？ |
| 第二層 紫微 | 這張卡用到的宮位、主星，是不是與紫微卡同一顆盤？ |
| 第三層 易經 | 這張卡的卦，是不是 `castHexagramFromBirth()` 出來的同一顆？`seedText` 可回查嗎？ |
| 無時辰路徑 | 有沒有代填時辰？有沒有硬起卦、硬排命宮？有沒有補救入口？ |
| 前端 | 有沒有自算數字、自編解讀、端出已被否認的宣稱？ |

### 已納入守門的卡片

**《桃花紅鸞心動》**（`test:three-core` 內含 8 條專屬斷言）

以 1990-05-20 21:30 女／亥時實測：

| 檢查 | 實測值 | 判定 |
|---|---|---|
| 年支／日支來源 | 午／酉，取自 `createBaziCore()` | ✓ |
| 日柱對獨立錨點 | 乙酉 | ✓ |
| 夫妻宮 vs 紫微卡 | 辰・天同（兩卡相同） | ✓ |
| 卦象 vs 易經層 | 山火賁（兩卡同卦） | ✓ |
| 格局名 | 山鎮抱火格 | ✓ |
| 起卦依據可回查 | `梅花易數\|1990-05-20\|時辰12` | ✓ |
| 無時辰路徑 | 不代填時辰、`ichingReading` 為 null、紫微 `UNAVAILABLE_BIRTH_TIME_REQUIRED`、有解鎖提示 | ✓ |

已做反向驗證：故意讓起卦偏移一個卦位，測試立即在卦象與格局名兩處報錯。

### 《靈魂配對》（雙人卡）

以 1990-05-20 亥時 女 × 1988-11-03 辰時 男 實測：

| 檢查 | 實測值 | 判定 |
|---|---|---|
| 第一層 A／B 日柱 | 乙酉／壬戌，皆對得上獨立錨點 | ✓ |
| 四柱來源 | `lib/bazi-engine.ts` → `buildBaziPillarsFromCore(createBaziCore())` | ✓ 走核心引擎 |
| 第二層 A 夫妻宮 | 辰・天同，與紫微卡、紅鸞卡同一顆盤 | ✓ |
| 兩人是否互相沾染 | 整張盤指紋不同（四柱、十二宮全異） | ✓ |
| 第三層 易經 | `UNAVAILABLE_RULE_SOURCE_REQUIRED`——雙人起卦規則尚未選定，**不生成卦象** | ✓ 誠實空缺 |
| 無時辰路徑 | **逐人分開判定**：A 有時辰給 A 的紫微，B 沒有就標需要時辰，日柱照給 | ✓ |
| 前端 | 無自算干支、無自編解讀、無已被否認的宣稱 | ✓ |

雙人卡的特別紅線：**不得因為是雙人卡，就把某一方的缺項用另一方補上。**

> 過程中我一度用「兩人命宮地支是否相同」判沾染，測試報錯後查證發現是真巧合——
> 十二宮只有十二個地支，兩張不同的盤命宮同支很常見。改用整張盤指紋比對才可靠。
> 判準寫錯也是一種錯，記在這裡免得下次重蹈。

### 《姓名學》（只有第一層與第三層）

第二層紫微本來就不在這張卡的範圍內，這不是缺失。
以 1990-05-20 亥時 女／王思妤 實測：

| 檢查 | 實測值 | 判定 |
|---|---|---|
| 第一層 四柱 | 庚午 辛巳 乙酉 丁亥，來源 `lib/nameology-bazi-crosscheck.ts` → `createBaziCore()` | ✓ |
| 日柱對獨立錨點 | 乙酉 | ✓ |
| 第三層 有時辰 | 山火賁，與紫微卡、紅鸞卡**同一顆生辰卦** | ✓ |
| 第三層 無時辰 | 改走**姓名象徵起卦**（水雷屯），不用生辰起卦 | ✓ |
| 無時辰四柱 | 時柱 `null`、標 `PARTIAL_BAZI`、三柱照給 | ✓ |
| 呈現層標示 | `method: "name-date-symbolic"`，不冒充生辰卦 | ✓ |
| 前端告知 | 「沒有補造出生時辰，也不等同傳統占筮」 | ✓ |

這張卡在第三層有一個特別漂亮的設計：**未知時辰時不用生辰起卦**——
因為生辰起卦需要時辰，硬用就等於補午時。改走姓名象徵起卦，並在呈現層與前端
都標明是哪一種起卦法。**寧可換一種方法，也不補造資料。**

守的紅線：兩種起卦法不得混為一談，也不得因為想給一顆卦就偷偷補時辰。

### 新增卡片時怎麼做

照抄 `tests/bazi-ziwei-cross.test.ts` 最後那一段〈逐卡三合一〉：
把該卡用到的引擎接進來，逐層比對即可。**沒有進守門測試的卡，不算做完三合一。**

## 八、後端運算檔案（鎖死用）

三合一不只活在測試與文件裡，它是**後端真正跑的那支引擎**：

### `lib/three-core-engine.ts`

```ts
import { computeThreeCore, assertThreeCoreConsistent } from '@/lib/three-core-engine';

const result = computeThreeCore({
  birthDate: '1990-05-20',
  gender: 'female',
  hourBranchIndex: 11,   // 0=子 … 11=亥；null 代表不知道時辰
});

assertThreeCoreConsistent(result);   // 三層對不起來就擋下，不讓它出去
```

| 回傳 | 內容 |
|---|---|
| `bazi` | 四柱、日主、年月日時支、三柱五行、四柱五行、節氣、農曆 |
| `ziwei` | `READY` 或 `UNAVAILABLE_BIRTH_TIME_REQUIRED`（附原因） |
| `iching` | `READY`（卦象＋格局名）或 `UNAVAILABLE_BIRTH_TIME_REQUIRED` |
| `crossCheck` | **引擎自己驗自己**的結果，含逐項明細與失敗原因 |
| `unlockNote` | 時辰未知時的補齊提示；已知時為 `null` |

### 引擎內建的自檢（每次呼叫都跑）

| 檢查 | 守什麼 |
|---|---|
| `BAZI_PILLARS_PRESENT` | 第一層四柱齊備 |
| `HOUR_NOT_FABRICATED` | **時辰未知時時柱必須是 null**，不得代填 |
| `ZIWEI_BAZI_MATCHES_CORE` | **第二層四柱必須等於第一層** |
| `ZIWEI_NOT_FORCED` | 時辰未知時不得硬排命宮 |
| `ICHING_SEED_TRACEABLE` | 起卦依據可回查 |
| `ICHING_PATTERN_DERIVED` | 格局名由卦象推出 |
| `ICHING_NOT_FORCED` | 時辰未知時不得硬起卦 |

`assertThreeCoreConsistent()` 用在「要把結果送去表達層／回傳前端」之前。
三層對不起來卻照樣輸出，就是那個 bug 能活這麼久的原因——**寧可擋掉，
不要讓客戶拿到互相矛盾的命盤。**

### 未知時辰的實測行為

```
四柱      庚午 辛巳 乙酉 null      ← 三柱照給，時柱不代填
紫微      UNAVAILABLE_BIRTH_TIME_REQUIRED
易經      UNAVAILABLE_BIRTH_TIME_REQUIRED
三柱五行  與已知時辰時完全相同     ← 與時辰無關，任何時候都成立
四柱五行  null                     ← 不給含推估時柱的版本
補齊提示  有
自檢      通過
```

### 反向驗證

故意讓第二層算出不同的月柱 → `test:three-core` 立即在六組案例全數報錯；
故意讓起卦偏移一個卦位 → 卦象與格局名兩處報錯。還原後 69/69 通過。

## 九、三合一整合控制層（鎖死用｜2026-09-05）

### 這一層不算命

三套系統全部沿用既有的，一行運算規則都沒有改寫。
整合層只做一件事：**把三套鎖成一條流程，互相核對，缺一不可，異常立即阻斷。**

檔案：`lib/three-in-one.ts`
守門：`npm run test:three-in-one`（70 項）、健檢第 21 項

### 最高層硬規則

```
完整結果 = 八字完成 && 紫微完成 && 易經完成 && 八字紫微四柱核對通過
```

四項缺一，完整結果禁止成立。不能發生「八字成功就直接顯示完整結果」。

### 流程（順序不可顛倒、不可跳關）

```
唯一出生資料 UnifiedInput
     ↓
呼叫既有八字            runBaziLayer      ← 四柱唯一來源
     ↓
呼叫既有紫微            runZiweiLayer
     ↓
八字 × 紫微 四柱交叉核對  verifyFourPillars ← 年月日時逐字，不容錯
     ↓  對不上就停在這裡
呼叫既有易經            runIChingLayer    ← 含正統卜卦儀式與起卦憑證
     ↓
三套狀態確認
     ↓
三合一成立，才允許輸出正式結果
```

### 狀態機

```
WAITING_INPUT → BAZI_RUNNING → ZIWEI_RUNNING → VERIFYING_FOUR_PILLARS
                                                  ├─ 通過 → YIJING_RUNNING → PASSED
                                                  └─ 不通過 → ABNORMAL（終點）
任何一關可以 → FAILED（終點）
```

`ABNORMAL` 與 `FAILED` 都是終點。**違規轉移當場丟例外**，不是靜靜地過去——
先前儀式關卡就是因為「順序自然成立」而變成擺設的。

### 四柱不一致時做什麼

只做三件事：**停下來、不顯示、原封不動報出去。**

**禁止自動把其中一套改成另一套。** 蓋掉之後畫面看起來正常，
但真正的問題（某段資料或傳遞跑掉）就再也找不到了——那是把「抓錯」變成「藏錯」。

報告要讓工程端看得懂是哪一柱、兩邊各是什麼：

```
{ pillar: 'month', bazi: '庚午', ziwei: '辛未' }
```

### 前端顯示

`components/ThreeInOneGate.tsx` 是一道**閘**，不是提示條：
完整結果放在 `children`，只有 `PASSED` 那一支會渲染它。
呼叫端就算忘了看 `display`，也沒辦法把半套結果端出去。

每一行文字都來自後端的 `ThreeInOneResult`，前端不編結論、不自己算、不自己組異常說明。

### 一個必須講清楚的限制

依本文件〈二〉的鐵律，紫微層現在也是呼叫 `lib/bazi/engine.ts` 取四柱，兩邊同源。
這道核對因此**抓不到「兩套演算法算出不同答案」**——系統裡已經只剩一套演算法，這是刻意的。

它抓得到的是**資料傳遞**出錯：兩邊拿到不同的生日或時辰、中途被改寫、
快取串味、或哪天有人又偷偷接了第二套排盤回來。
歷史上真正出事的那次正是這一類（餵錯曆法），所以這道閘留著有意義，
但不要把它當成「演算法互相驗證」。

## 十、神獸卡遊戲核心（口令「神獸卡遊戲」｜2026-09-05）

### 一句話

一個遊戲核心、一套卡片格式、一套技能系統、一套效果系統、一套戰鬥規則。
**以後新增神獸卡＝新增資料，不是重寫程式。**

### 架構

```
cards/beasts/*.ts     卡片資料（一張一個檔）
cards/skills/index.ts 技能登錄中心
        ↓
lib/beast-game/
  schema.ts    卡片格式＋品質驗證（不合格禁止進正式牌庫）
  elements.ts  五元素（接平台既有對照，不另立第二套）
  registry.ts  卡片登錄中心
  effects.ts   效果核心（13 種 EffectType，唯一會改狀態的地方）
  battle.ts    戰鬥核心（傷害公式、技能觸發、出手順序）
  turn.ts      回合核心＋牌組系統（七階段轉移表、種子亂數）
  balance.ts   平衡評分（Power Budget／BALANCE_WARNING）
  index.ts     BeastCardGameCore 對外唯一入口
```

守門：`npm run test:beast-game`（156 項）、健檢第 23 項

### 怎麼加一張卡

1. `cards/beasts/<slug>.ts` 照 `BeastCard` 寫資料
2. `lib/beast-game/registry.ts` 的 `REGISTERED` 加一行
3. 跑 `npm run test:beast-game`

驗證不過就進不了正式牌庫——這是真的擋，不是印警告。
**任何一支引擎都不用改。**

### 怎麼加一個技能

`cards/skills/index.ts` 加一筆，`effects` 只能用既有的 13 種 EffectType。
Battle Engine 不認得任何技能的名字（測試會擋），所以加技能不必動它。

### 幾條硬規則

| 規則 | 實作位置 |
|---|---|
| 前端不准自己扣血、算勝負 | 全部在 `battle.ts`／`effects.ts`，純函式無 React |
| 動畫不得決定戰鬥結果 | `GameState.timeline` 先算完，前端照著播 |
| 七階段不得跳關 | `turn.ts` 的 `NEXT_PHASE` 轉移表，違規丟例外 |
| 同一招不得無限放 | `usesPerBattle` + `SkillUsage` |
| 稀有度不等於絕對戰力 | `rarityIsNotPower()`，預算帶必須重疊 |
| 手牌不得載高清圖 | 三段式 `thumbnail`／`front`／`high`，測試比對檔案大小 |
| 同一場要能重現 | 種子亂數，同 seed 同結果（可回查客訴） |

### 第一階段實測（6 張卡）

```
角木蛟 SR 296  亢金龍 SSR 296  氐土貉 N 277
房日兔 R  275  心月狐 R   299  尾火虎 SR 321
稀有度重疊：N最高277 vs R最低275／R最高299 vs SR最低296／SR最高321 vs SSR最低296
縮圖 26–33KB（原圖 2.8MB），手牌只載縮圖
```

### 過程中被自己的檢查抓到的兩件事

1. **稀有度變成絕對戰力**：第一版數值排出來 SR 最低 310 > R 最高 286，
   `rarityIsNotPower()` 直接報錯。調整 SR 下修、R 上修才通過。
2. **常駐被動把預算炸掉**：被動用 `duration: 99` 表示常駐，
   技能分算出 588，比整張卡的數值分還高三倍。改成邊際遞減並封在四回合。

兩件都不是「感覺怪怪的」，是算出來的數字報錯。這就是第十九條要的效果。
