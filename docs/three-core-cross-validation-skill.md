# 三核心交叉技能｜八字命盤 × 紫微斗數 × 易經卜卦

> **口令：「三合一」**
>
> 使用者只要說「三合一」，就代表這三樣：**八字命盤、紫微斗數、易經卜卦**。
> 收到口令即執行下方〈六、三合一執行程序〉。

> 定案 2026-09-04。這是命理運算的架構鐵律，任何新卡片、任何引擎改動都適用。

---

## 一、三層順序（不可顛倒）

```
第一層  八字命盤   核心。唯一的四柱來源。
   ↓
第二層  紫微斗數   第二輪。消費第一層，不得自行推算四柱。
   ↓
第三層  易經卜卦   第三輪。只負責「怎麼說」。
   ↓
        前端      只顯示。不編結論、不自己算、不自己寫解讀。
```

**一切以八字命盤為主。** 前一層算完並凍結之後，後一層才開始；後一層永遠不能回頭改寫前一層的結論。

---

## 二、每一層的職責與禁令

### 第一層｜八字命盤（核心）

| | |
|---|---|
| 唯一入口 | `lib/bazi/engine.ts` 的 `createBaziCore()` |
| 產出 | 年、月、日、時四柱、日主、十神、藏干、大運 |
| **禁令** | **任何模組不得自己再實作一套四柱推算** |

年界以立春、月界以節氣、晚子時不換日——這些規則只存在於這一支引擎裡。

**判準素材**（專業命理師客訴後永久鎖定，`tests/bazi-core.test.ts`）：

```
1974-07-02 03:30 女 → 甲寅／庚午／甲辰／丙寅
  月柱＝庚午：小暑(7/7)前仍屬午月，甲年五虎遁，不是辛未
對照組 1974-07-08 → 辛未（小暑後）
```

### 第二層｜紫微斗數

| | |
|---|---|
| 排盤入口 | `lib/ziwei/chartEngine.ts` 的 `generateZiweiChart()` |
| 三方四正 | `lib/ziwei-sanfang-engine.ts` |
| 八字欄位 | **必須取自第一層**，不得自算 |
| **禁令** | 時辰未確認時不得硬排命宮，也不得代填午時 |

排盤本身（命宮、十二宮、十四主星、四化）獨立於八字，但凡是回應裡出現的四柱，一律來自第一層。

### 第三層｜易經卜卦

| | |
|---|---|
| 起卦 | `lib/iching-engine.ts` 的 `castHexagramFromBirth()`（梅花易數，決定性） |
| 格局名 | `lib/iching-psychology.ts` 的 `patternNameOf()` |
| 話術 | `buildEmpathicFromHexagram()` 等共感層 |
| **禁令** | **不新增規則、不改寫證據**。哪個月、哪個方向，全部來自前兩層 |

現成正確範例：`lib/red-luan-iching-reading.ts` 開頭的分層宣告。

**話術由這一層產出，交給前端顯示。** 這是「前端不准編結論」的正面說法——不是叫前端別寫，是告訴它「文案在易經層，去拿」。

### 前端

只顯示。三條紅線：

1. 不得自己計算任何看起來像運算結果的數字
2. 不得自己寫解讀文字（要就放進易經層）
3. 不得端出系統自己否認的宣稱

## 三、鐵律＝必生 CI 測試

> **以後只要立下這種鐵律，就要同時生出一支 CI 測試。**

沒有測試的鐵律等於沒有鐵律。紫微卡的日柱錯了不知道多久，就是因為當時只有口頭原則、沒有機器在守。

現行守門測試：`npm run test:three-core`（41 項斷言）

| 層級 | 斷言 |
|---|---|
| 八字 × 紫微 | 6 組生辰的四柱必須完全一致 |
| 獨立錨點 | 日柱必須對得上 1974-07-02＝甲辰 的純日數推算（不經任何命理引擎） |
| 卡內一致 | `meta.dayPillar` 與 `ziweiSanFang.bazi.day` 不得矛盾 |
| 正統鎖定 | 1974-07-02 逐柱釘死＝甲寅／庚午／甲辰／丙寅 |
| 易經決定性 | 同一生辰起卦 50 次必須完全相同 |
| 易經可回查 | `seedText` 必須帶生辰與時辰 |
| 易經有效性 | 時辰不同必須是不同的卦；不同生辰不得塌成同一卦 |

邊界覆蓋：節氣換月前後一天、晚子時、閏年 2/29、跨年 12/31。

**新增鐵律時的最低要求**：一個正向案例、一個邊界案例、一個**反向驗證**（故意注入該類錯誤，確認測試會爆）。

---

## 四、這條鐵律怎麼來的

2026-09-04 巡檢《易經紫微斗數》時發現：

`lib/ziwei-sanfang-engine.ts` 用 `tyme4ts` 的 `LunarHour.fromYmdHms()` 自行重算了一份八字，
而該 API 吃的是**農曆**、程式卻餵**國曆**。1990-05-20 被當成農曆五月二十（實際國曆 6/12），
整整差 23 天：日柱算成戊申（正確乙酉）、日主變成戊土（正確乙木），整段流年生剋關係相反。

最致命的是——同一份回應裡 `meta.dayPillar` 是對的、`ziweiSanFang.bazi.day` 是錯的。
兩套八字各自內部一致，所以**各自的測試都過**，因為從來沒有人把它們放在一起比對。
客戶只要拿八字卡與紫微卡對照一次就會發現。

問題不是演算法錯，是**同一件事被算了兩次，而沒有人負責比對**。
所以鐵律不是「要算對」，是「**只准算一次，而且要有機器守著**」。

## 五、新增卡片時的檢查清單

- [ ] 需要四柱嗎？→ 呼叫 `createBaziCore()`，不要自己寫
- [ ] 需要命盤嗎？→ 呼叫 `generateZiweiChart()`，八字欄位取自第一層
- [ ] 需要話術嗎？→ 寫在易經層，前端只顯示
- [ ] 前端有沒有自己算的數字或自己寫的解讀？→ 搬回引擎
- [ ] 有沒有端出後端否認過的宣稱？→ 拿掉
- [ ] 這張卡的四柱有沒有進 `test:three-core`？→ 加進去
- [ ] 新鐵律有沒有對應的 CI 測試？→ 沒有就不算立法完成

## 六、三合一執行程序

收到口令「三合一」時，依序執行並回報：

### 步驟 1｜跑守門測試
`npm run test:three-core` — 41 項斷言必須全綠。有紅就先停，報告哪一項。

### 步驟 2｜同一組生辰實跑三層
用同一筆出生資料，依序取得三層輸出並逐項核對：

| 檢查 | 判準 |
|---|---|
| 第一層 八字四柱 | 對得上獨立錨點（1974-07-02＝甲辰，純日數推算） |
| 第二層 紫微四柱 | 必須與第一層**完全一致** |
| 卡內一致 | `meta.dayPillar` 不得與 `ziweiSanFang.bazi.day` 矛盾 |
| 第三層 易經卦象 | 決定性、可回查、時辰不同必不同卦 |
| 前端 | 沒有自編結論、沒有自算數字、沒有已被否認的宣稱 |

### 步驟 3｜三大核心對照（米其林）
- **品質**：前端不准編結論
- **服務**：免費也要尊榮
- **穩定**：沒驗過不准上線

### 步驟 4｜回報
逐層列出實測值（不是「應該正常」），有問題就給 P0/P1/P2/P3 分級與解法。
**不得只報結論不附數據。**

## 七、逐卡三合一（方法要能對準單一張卡）

「三合一」不只是跑一次全域檢查——它是**方法**，要能對準任何一張卡，
驗那張卡自己的八字、紫微、易經是否與三個核心一致。

### 逐卡檢查表

| 層級 | 對這張卡問什麼 |
|---|---|
| 第一層 八字 | 這張卡的四柱／年支／日支，是不是來自 `createBaziCore()`？有沒有自己算一套？ |
| 第二層 紫微 | 這張卡用到的宮位、主星，是不是與紫微卡同一顆盤？ |
| 第三層 易經 | 這張卡的卦，是不是 `castHexagramFromBirth()` 出來的同一顆？`seedText` 可回查嗎？ |
| 無時辰路徑 | 有沒有代填時辰？有沒有硬起卦、硬排命宮？有沒有補救入口？ |
| 前端 | 有沒有自算數字、自編解讀、端出已被否認的宣稱？ |

### 已納入守門的卡片

**《桃花紅鸞心動》**（`test:three-core` 內含 8 條專屬斷言）

以 1990-05-20 21:30 女／亥時實測：

| 檢查 | 實測值 | 判定 |
|---|---|---|
| 年支／日支來源 | 午／酉，取自 `createBaziCore()` | ✓ |
| 日柱對獨立錨點 | 乙酉 | ✓ |
| 夫妻宮 vs 紫微卡 | 辰・天同（兩卡相同） | ✓ |
| 卦象 vs 易經層 | 山火賁（兩卡同卦） | ✓ |
| 格局名 | 山鎮抱火格 | ✓ |
| 起卦依據可回查 | `梅花易數\|1990-05-20\|時辰12` | ✓ |
| 無時辰路徑 | 不代填時辰、`ichingReading` 為 null、紫微 `UNAVAILABLE_BIRTH_TIME_REQUIRED`、有解鎖提示 | ✓ |

已做反向驗證：故意讓起卦偏移一個卦位，測試立即在卦象與格局名兩處報錯。

### 新增卡片時怎麼做

照抄 `tests/bazi-ziwei-cross.test.ts` 最後那一段〈逐卡三合一〉：
把該卡用到的引擎接進來，逐層比對即可。**沒有進守門測試的卡，不算做完三合一。**

## 八、後端運算檔案（鎖死用）

三合一不只活在測試與文件裡，它是**後端真正跑的那支引擎**：

### `lib/three-core-engine.ts`

```ts
import { computeThreeCore, assertThreeCoreConsistent } from '@/lib/three-core-engine';

const result = computeThreeCore({
  birthDate: '1990-05-20',
  gender: 'female',
  hourBranchIndex: 11,   // 0=子 … 11=亥；null 代表不知道時辰
});

assertThreeCoreConsistent(result);   // 三層對不起來就擋下，不讓它出去
```

| 回傳 | 內容 |
|---|---|
| `bazi` | 四柱、日主、年月日時支、三柱五行、四柱五行、節氣、農曆 |
| `ziwei` | `READY` 或 `UNAVAILABLE_BIRTH_TIME_REQUIRED`（附原因） |
| `iching` | `READY`（卦象＋格局名）或 `UNAVAILABLE_BIRTH_TIME_REQUIRED` |
| `crossCheck` | **引擎自己驗自己**的結果，含逐項明細與失敗原因 |
| `unlockNote` | 時辰未知時的補齊提示；已知時為 `null` |

### 引擎內建的自檢（每次呼叫都跑）

| 檢查 | 守什麼 |
|---|---|
| `BAZI_PILLARS_PRESENT` | 第一層四柱齊備 |
| `HOUR_NOT_FABRICATED` | **時辰未知時時柱必須是 null**，不得代填 |
| `ZIWEI_BAZI_MATCHES_CORE` | **第二層四柱必須等於第一層** |
| `ZIWEI_NOT_FORCED` | 時辰未知時不得硬排命宮 |
| `ICHING_SEED_TRACEABLE` | 起卦依據可回查 |
| `ICHING_PATTERN_DERIVED` | 格局名由卦象推出 |
| `ICHING_NOT_FORCED` | 時辰未知時不得硬起卦 |

`assertThreeCoreConsistent()` 用在「要把結果送去表達層／回傳前端」之前。
三層對不起來卻照樣輸出，就是那個 bug 能活這麼久的原因——**寧可擋掉，
不要讓客戶拿到互相矛盾的命盤。**

### 未知時辰的實測行為

```
四柱      庚午 辛巳 乙酉 null      ← 三柱照給，時柱不代填
紫微      UNAVAILABLE_BIRTH_TIME_REQUIRED
易經      UNAVAILABLE_BIRTH_TIME_REQUIRED
三柱五行  與已知時辰時完全相同     ← 與時辰無關，任何時候都成立
四柱五行  null                     ← 不給含推估時柱的版本
補齊提示  有
自檢      通過
```

### 反向驗證

故意讓第二層算出不同的月柱 → `test:three-core` 立即在六組案例全數報錯；
故意讓起卦偏移一個卦位 → 卦象與格局名兩處報錯。還原後 69/69 通過。
